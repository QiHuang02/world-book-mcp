# 开场白规则

first_mes 必须提供场景钩子、角色当前状态、`{{user}}` 可介入方向。

## 长度要求

- `first_mes` 至少 400 个非标点字符。
- 计数时中文、英文、数字、占位符字符计入；空白、换行和标点符号不计入。
- alternate greetings 不强制 400 字，但仍应完整呈现场景钩子与互动空间。
- 400 字限制属于 skill 内容规范，不是 MCP 结构校验；写作和交付自查时必须执行。
- 300-500 / 500-800 / 800-1500 字分级可作节奏参考，但 MCP 成品 `first_mes` 仍以至少 400 个非标点字符为硬性自查标准。

## `{{user}}` 占位符

- 开场白中只要让 user 出场、被称呼、被等待、被邀请、被观察、被交付任务或可介入，必须写字面占位符 `{{user}}`。
- 不使用 `<user>`、`用户`、`你`、`您`、`你们`、`对方`、`来客` 等替代占位符。
- 可以描写角色面向 `{{user}}` 的动作和可回应契机，但不得替 `{{user}}` 决定说话、动作、外貌、性别、身份、职业、房间、性格或后续选择。
- 若二创任务明确要求 user 扮演原著既有角色，仍优先在开场白里用 `{{user}}`，把扮演关系写入 plan 或世界书设定，不把原角色名替代占位符。

## 场景化开场原则

1. **场景化开场**：不要只有问候或自我介绍，而是设计具体、生动、可感知的开场场景。
2. **融入角色设定**：让性格、背景关键经历、当前目标、人际关系和情绪状态通过行动与对白自然出现。
3. **上下文关联**：与世界观、角色关系、MVU 初始状态和用户要求一致。
4. **沉浸式环境**：提供时间、地点、氛围、声音、气味、物件、角色正在做的活动。
5. **符合人设的对话**：角色对白必须符合语言习惯、态度和肢体行为。
6. **自然引导互动**：通过问题、请求、悬念、冲突或可触碰物件让 `{{user}}` 有明确回应空间。

## 写法要点

- 保持 `{{user}}` 的说话和行动开放。
- `{{user}}` 外貌、性别、房间、职业、性格由用户决定。
- 结尾给开放式选择或可回应动作。
- 开场白以场景推进为主，设定信息只保留当前场景需要的部分。
- 先给时间/地点/可感知环境。
- 展示角色正在做什么。
- 用角色动作、物件、空间关系制造互动入口，不用旁白替 `{{user}}` 下结论。
- 前 3 行优先制造吸引力：悬念、反常细节、情绪拉力或未解决的现场问题。
- 避免平淡自我介绍、设定信息堆砌、视角混乱、抽象环境描写和没有互动钩子的单向叙述。

## MVU/HTML

启用 MVU 或 HTML 状态栏时必须包含：

```text
<StatusPlaceHolderImpl/>
```

技术资产修复时也不能忽略占位符规则：开场白、alternate greetings、世界书条目中面向 user 的“你/你的/客人”等指代都要改成字面 `{{user}}`，且不替 `{{user}}` 决定动作、身份或外貌。

开场白状态必须与 `mvu-initvar` 一致：地点、时间、关系、资源、任务进度、情绪、好感/信任/敌意等初始变量不得与开场白冲突。

alternate greeting 若包含：

```xml
<UpdateVariable><initvar>...</initvar></UpdateVariable>
```

必须确认 YAML 可解析，并说明它会覆盖默认 initvar。

## 自查

- 去掉标点和空白后，`first_mes` 是否至少 400 字符？
- 是否所有 user 指代都写成了 `{{user}}`？
- 是否没有使用 `<user>`、`用户`、`你`、`您`、`你的`、`你们`、`对方`、`客人`、`来客` 等替代写法？
- 是否没有预设 `{{user}}` 的身份、外貌、动作、房间或下一步选择？
- 前 3 行是否有悬念、反常细节或情绪拉力？
- 是否有时间/地点/环境、角色当前动作、可回应的互动入口？
- 启用 MVU/HTML 时，是否保留 `<StatusPlaceHolderImpl/>` 且状态栏变量不使用裸 `{{stat_data...}}`？
- MVU 初始变量是否与开场白时点一致？
- 结尾是否给出可接续的互动契机，而不是替 `{{user}}` 回答或行动？
